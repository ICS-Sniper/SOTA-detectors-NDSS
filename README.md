# ICS Attack Detectors against ICS-Sniper

Archived as part of the ICS-Sniper artifact: https://doi.org/10.5281/zenodo.23737012

This artifact evaluates network-based and process log-based intrusion detectors against attacks generated by ICS-Sniper. It contains preprocessed IPAL datasets, detector configurations, experiment notebooks, evaluation utilities, and a notebook workflow for training, attack detection, evaluation, and plotting, with optional benign validation. The quick start defaults to the publicly reproducible detector subset.

The implementation builds on the [IPAL IIDS Framework](https://github.com/fkie-cad/ipal_ids_framework) and its ensemble strategies.

## Reproducibility scope

The public repository supports the end-to-end workflow for the public subset below. The InvariantRules and PASAD implementations used in our experiments are not distributed with this artifact. Their configuration files are included for reference; configuration files alone do not provide the implementations.

| Detector or ensemble | Public subset (`public`, default) | Complete detector suite (`full`) |
| --- | --- | --- |
| InterArrivalTimeMean, InterArrivalTimeRange, Kitsune | Included | Included |
| Network Any/All ensembles | Included | Included |
| Histogram, MinMax, SteadyTime | Included | Included |
| Public process Any/All over Histogram, MinMax, SteadyTime | Included (`Any-public`, `All-public`) | Uses the original process ensembles below instead |
| InvariantRules, PASAD | Excluded | Requires separately obtained implementations |
| Original process Any/All with InvariantRules and PASAD | Uses the public process ensembles above instead | Requires both InvariantRules and PASAD |

The public subset includes reproducible process Any/All ensembles built exclusively from Histogram, MinMax, and SteadyTime. Reproducing results involving those non-public implementations requires the complete detector suite described below.

## Environment setup

Clone the repository and enter its root directory, then create the development environment:

```bash
./setup_development_venv.sh
source ./activate_ipal.sh
```

The setup script creates an ignored `ipal-dev/` virtual environment.

## Quick start: publicly reproducible subset

### 1. Run a minimal command-line example

First verify the environment with a single public process detector. From the repository root, this S3 MinMax example uses the same training data, attack input, ground truth, and detector configuration as `quick_start.ipynb`:

```bash
ipal-iids --retrain \
    --config config/quick_start/S3/minmax.config \
    --train.state dataset/20260411-clean/full_training.state.gz \
    --live.state dataset/scenario-3-attack/S3_att.state.gz \
    --output output.state.gz

ipal-evaluate \
    output.state.gz \
    --attacks dataset/scenario-3-attack/1_attacks.json \
    --output output.json

ipal-plot-alerts \
    output.state.gz \
    --attacks dataset/scenario-3-attack/1_attacks.json \
    --output S3-minmax-alerts.png
```

This example does not require the non-public InvariantRules or PASAD implementations. A successful run creates `output.state.gz`, `output.json`, and `S3-minmax-alerts.png` in the repository root.

### 2. Run the notebook workflow

Start Jupyter from the repository root:

```bash
jupyter notebook quick_start.ipynb
```

Keep the default mode, select a scenario from 1 to 5, and run the cells from top to bottom:

```python
DETECTOR_MODE = "public"
```

The notebook checks inputs, trains the public detectors on the selected benign data, runs attack detection, evaluates the outputs, and creates separate network and process alert plots. It uses the already tuned configurations; training learns the models from benign inputs rather than searching configuration hyperparameters. The default workflow skips the separate benign-validation experiment.

Network Any/All use the public network detectors. Process plots contain Histogram, MinMax, SteadyTime, `Any-public`, and `All-public`.
All benign training data, attack inputs, and attack ground truth required by the five scenarios are included under `dataset/`.

## Optional: complete detector suite

This mode includes the same individual public detectors and adds InvariantRules and PASAD. This mode requires obtaining the experiment implementations separately from the IPAL authors and installing their additional dependencies in the environment used by `ipal-iids`.

Place the implementations, including their supporting modules, under:

```text
ipal_ids_framework/ids/invariant_rules/  # entry point: invariant_rules_IDS.py
ipal_ids_framework/ids/pasad/            # entry point: Pasad.py
```

In `quick_start.ipynb`, select:

```python
DETECTOR_MODE = "full"
```

Restart the kernel and run all cells after changing modes.

## Optional: benign validation

The final section of `quick_start.ipynb` measures false positives on held-out benign runs. It is disabled by default, including when running all cells. To enable it, set `RUN_BENIGN_VALIDATION = True` in the final code cell and run that cell after completing the main workflow.

This optional step requires at least two numbered benign message files and two numbered benign state files. It randomly selects separate training and validation runs and writes results to `quick_start_result/<mode>/validation/`. It does not tune configuration hyperparameters, and its trained models are not reused by attack detection.

## Optional raw-data transcription

Users who want to reproduce the preprocessing step can run `dataset/transciber.ipynb`. The notebook uses the raw `dataset/transcriber/S3_att.csv` and `dataset/transcriber/S3_att.pcap` files as examples and generates `S3_att.state.gz` and `S3_att.ipal.gz`, respectively.

The notebook demonstrates four separate steps:

1. Normalize the CSV columns and transcribe the process log to IPAL state records.
2. Transcribe the Modbus PCAP with `ipal-transcriber` and the included `dataset/transcriber/rules-modbus.py` rules file that is only applicable to the ICS-Sniper hardware testbed.
3. Run `_ensure_ipal_timestamp_order` to detect and correct out-of-order network records.
4. Run `ipal-add-attacks` to annotate the generated datasets with attack intervals.

## Quick-start outputs

Each mode has its own output directory: `utils/scenario-<S>-attack/quick_start_result/<mode>/`, where `<mode>` is `public` or `full`. Attack outputs, evaluation JSON files, logs, and the figures `S<S>-networkDetectors.png` and `S<S>-stateDetectors.png` are stored directly in the mode directory. Figure titles identify the selected mode.

## Repository layout

- `quick_start.ipynb`: entry point for one scenario, with public-subset and optional complete-suite modes.
- `dataset/<date>/`: benign message and process-state training data used by the five scenarios.
- `dataset/scenario-<S>-attack/`: attack ground truth and preprocessed message/state attack inputs for S1-S5.
- `dataset/transciber.ipynb`: optional CSV/PCAP transcription, timestamp-order correction, and attack-labeling workflow.
- `dataset/transcriber/`: raw S3 transcription examples and the Modbus rules file.
- `config/`: baseline detector configurations.
- `config/quick_start/S<S>/`: self-contained detector and ensemble configurations selected for each scenario.
- `config/quick_start/S<S>/all_p_pub.config`, `combiner-All_p_pub.config`: three-model public process ensembles and their All combiner; Any reuses `combiner-Any.config`.
- `utils/scenario-<S>-attack/quick_start_result/<mode>/`: generated quick-start results, separated by execution mode.
- `ipal_ids_framework/`: public detector implementations; experiment-specific InvariantRules and PASAD implementations are not distributed.
- `ipal_evaluate/`: evaluation and plotting tools.

The `utils/` directory is intentionally excluded from this release branch. `quick_start.ipynb` creates all required runtime directories automatically.
